# ASC CLI opportunities for OpenASO

Checked 26 October 2026 against primary upstream source and Apple documentation. This is a research note; no upstream implementation is copied and no application credentials or store metadata are changed.

## Version and scope

The installed `asc version` reports **5.14.0**. GitHub's latest-release API reports **5.17.0**, published **25 October 2026 at 22:49:09 UTC**, with source commit `ecad9f122524248749b6c44bb01e951734131889`. The intervening releases mainly improve authentication recovery, diagnostics, security, and resource reads. The directly relevant new 5.17 feature is custom product page keyword validation. Broader keyword discovery and optimization features below also exist in the current CLI, but should not all be described as newly introduced since 5.14. [5.17.0 release](https://github.com/rorkai/App-Store-Connect-CLI/releases/tag/5.17.0), [5.16.0 release](https://github.com/rorkai/App-Store-Connect-CLI/releases/tag/5.16.0), [5.15.0 release](https://github.com/rorkai/App-Store-Connect-CLI/releases/tag/5.15.0).

OpenASO's current branch already implements saved-credential keyword suggestions, seeded/paged expansion, independent market popularity, authenticated metadata snapshots, relevance and coverage audits, draft comparison, and immutable local release baselines. Acquisition counts in those baselines are caller-provided. The retained competition estimator and persistence types are a foundation that still needs production wiring; their existence does not mean current MCP audits produce fresh competition evidence. See `README.md`, `OpenASO/Services/MCP/KeywordTargetingAnalysis.swift`, and `OpenASO/Services/SearchRanking/KeywordDifficultyEstimator.swift`.

## Recommended additions before release

### 1. Expand discovery with official phrase suggestions

ASC combines app keyword suggestions with **phrase suggestions**, whereas OpenASO currently calls only the keyword endpoint. Apple offers a second read-only discovery surface at `POST /v1/suggestions/phrases/query`, including app discovery and partial-text searches. This is a direct fit for finding more relevant, longer queries. [ASC discovery design](https://github.com/rorkai/App-Store-Connect-CLI/blob/5.17.0/docs/design/optimize-keywords.md), [Apple suggestion endpoints](https://developer.apple.com/documentation/apple-ads-platform-api/suggestions-endpoints).

Implementation can reuse the pinned **Apple Ads Swift SDK v1.109.0** and saved Apple Ads account credentials. That version already exposes `queryPhraseSuggestions(headers:body:)`; a dependency upgrade is unnecessary. Discovery needs filters `queryType=SUGGESTION`, `promotedObjectId=<app ID>`, and `promotedObjectType=APPSTORE_APP`. Branching can use `queryType=SEARCH` with `phrase LIKE`; exact lookup uses `phrase IN`. The search route does not need an app ID. No campaign is required. [Pinned SDK generated client](https://github.com/apple/apple-ads-platform-api-swift/blob/v1.109.0/Sources/AppleAdsClient/Generated/Client.swift), [Apple phrase query contract](https://developer.apple.com/documentation/apple-ads-platform-api/query-phrase-suggestions).

The result has optional `phrase` and `popularity`. Neither the phrase result nor its documented filters includes a country dimension. Keep that contextual score separate from the existing country-specific popularity lookup, and pass newly discovered phrases through that lookup before recommending additions. Do not describe phrase scores as local search volume. The SDK exposes request `offset`/`pageSize` and response `offset`/`pageSize`/`totalCount`; retain independent source pagination and deduplicate across both endpoints. [SDK response and request types](https://github.com/apple/apple-ads-platform-api-swift/blob/v1.109.0/Sources/AppleAdsClient/Generated/Types.swift), [ASC source scope and bounded discovery](https://github.com/rorkai/App-Store-Connect-CLI/blob/5.17.0/internal/cli/optimize/keywords_discover.go).

Release-sized scope: one provider method, source-aware DTOs/pagination, MCP expansion and skill guidance. Bound phrase discovery independently, fetch app-wide phrases once per app/page rather than repeating them for each storefront, preserve successful keyword results if phrases fail, and omit popularity sorting because live APIs have rejected that sort despite examples suggesting it. No persistent schema change is required. [ASC observed request handling](https://github.com/rorkai/App-Store-Connect-CLI/blob/5.17.0/internal/cli/ads/search_optimization.go).

Live qualification: read-only probes for both monitored apps returned working keyword suggestions, while each app-associated phrase source returned HTTP 400 indicating that the promoted app was missing or inaccessible to the ad account. The documented app-independent `SEARCH` route then accepted four `phrase LIKE` queries (`dictation`, `voice`, `focus`, and the documented example `productivity`) but returned zero phrases in every case. The unadorned LIKE syntax matches Apple's documented example. Existing Ads credentials therefore do not guarantee useful phrase results. Preserve partial source failures and zero-result evidence; treat phrase support as experimental until it demonstrates incremental candidates for this account. It should not delay this release on an unsupported claim of better coverage. Raw probes remain outside the repository. Installed 5.14 supports `asc ads suggestions phrases find --file <query.json> --ads-profile <profile>` for these checks.

### 2. Connect competition evidence to the shortlist and targeting audit

The CLI evaluates candidate reachability from competitor evidence as well as demand. OpenASO already retains its own top-ten rating-authority and metadata-saturation estimator with confidence and evidence types. Wire that foundation into bounded native ranking samples, then show difficulty, confidence, sample count, source, time, and relevant competitor examples alongside popularity and metadata gaps. This helps distinguish a popular term from a practical target. This is an application analysis heuristic, not an Apple-provided difficulty metric. [ASC evaluation methodology and limitations](https://github.com/rorkai/App-Store-Connect-CLI/blob/5.17.0/docs/design/optimize-keywords.md).

Reuse OpenASO's estimator instead of importing ASC's alternative formula. Treat absent ratings, too few results, stale samples, and iTunes fallback as explicit limitations; they must not become an easy-keyword score. Read-only audits should calculate ephemeral evidence without silently storing refresh data. Persist evidence only through an explicit refresh path. Release scope is moderate because production integration is missing even though model types exist. Avoid a database migration merely to expose a read-only audit result.

### 3. Protect custom product page keyword assignments

ASC 5.17 adds an advisory check for assigned custom page keywords absent from the selected app version's same-locale keyword field. Apple allows custom pages to appear for assigned keywords from the latest approved version, so a draft that removes an assigned term needs a visible warning. This extends OpenASO's current draft protection beyond title/subtitle demotion and existing native winners. [5.17 feature and correction](https://github.com/rorkai/App-Store-Connect-CLI/releases/tag/5.17.0), [Apple custom page configuration](https://developer.apple.com/help/app-store-connect/create-custom-product-pages/configure-multiple-product-page-versions).

Use the existing App Store Connect JWT provider for a read-only resource chain:

1. `GET /v1/apps/{app}/appCustomProductPages`.
2. `GET /v1/appCustomProductPages/{page}/appCustomProductPageVersions`.
3. `GET /v1/appCustomProductPageVersions/{version}/appCustomProductPageLocalizations`.
4. Read included search keyword relationship IDs, checking completeness; alternatively list `GET /v1/appCustomProductPageLocalizations/{localization}/searchKeywords` with pagination.

Apple documents the [app/page resources](https://developer.apple.com/documentation/appstoreconnectapi/app-custom-product-pages), [page versions](https://developer.apple.com/documentation/appstoreconnectapi/app-custom-product-page-versions), [localizations](https://developer.apple.com/documentation/appstoreconnectapi/app-custom-product-page-localizations), and [keyword read](https://developer.apple.com/documentation/appstoreconnectapi/get-v1-appcustomproductpagelocalizations-_id_-searchkeywords).

The verified ASC behavior is **iOS/iPadOS only**, excluding replaced page versions. It compares each keyword as a normalized whole phrase against comma-separated keyword entries in the same locale; title/subtitle token combinations are not a substitute. Read failures or incomplete relationships produce **unverified**, rather than a clean pass. ASC uses `limit[searchKeywords]=50` on included relationships and validates reported totals. Implement from Apple's contract rather than copying ASC code. Bound page/version/localization reads and preserve partial evidence. No page assignment, publishing, or metadata write is needed. [ASC read integration](https://github.com/rorkai/App-Store-Connect-CLI/blob/5.17.0/internal/cli/validate/custom_product_pages.go), [iOS and failure guards](https://github.com/rorkai/App-Store-Connect-CLI/blob/5.17.0/internal/cli/validate/readiness.go), [phrase membership check](https://github.com/rorkai/App-Store-Connect-CLI/blob/5.17.0/internal/validation/custom_product_pages.go).

## Measurement boundaries that affect recommendations

`asc analytics compare` currently accepts **Sales** as its comparison source. `asc insights weekly --source analytics` summarizes report/instance availability and explicitly leaves business conversion unavailable; it does not parse acquisition metrics from report payloads. Copying those commands' surface alone would not deliver automatic ASO impact measurement. [Analytics comparison source](https://github.com/rorkai/App-Store-Connect-CLI/blob/5.17.0/internal/cli/analytics/analytics_compare.go), [insights implementation](https://github.com/rorkai/App-Store-Connect-CLI/blob/5.17.0/internal/cli/insights/insights.go).

Paid search-term reports can identify queries with actual taps and installs, which is stronger paid-conversion evidence than popularity alone. ASC's optimization plan joins these reports with suggestions, targeting, and impression share. This is useful only when the account has relevant campaign history; it neither establishes organic conversion nor guarantees that a metadata edit improves ranking. Keep it a separate later tool with paid provenance. [ASC cross-API plan](https://github.com/rorkai/App-Store-Connect-CLI/blob/5.17.0/docs/design/official-search-optimization-plan.md), [Apple search-term reporting guidance](https://developer.apple.com/documentation/apple-ads-platform-api/journey-app-store-ads).

No verified recent ASC release introduces a new country-specific popularity source that eliminates low/floor values. Phrase discovery broadens candidates; relevance, independent market-popularity verification, native ranking evidence, and competition assessment remain necessary.
